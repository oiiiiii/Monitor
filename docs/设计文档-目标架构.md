# 设计文档（目标架构 / 早期方案稿）

> **注意**：本文档写于项目立项阶段，描述的是 RabbitMQ + TDengine + PostgreSQL 的微服务架构设想。
> 实际交付版本已收敛为 `monitor-standalone` 单体实现（SQLite + 本地波形文件），
> 文中提到的队列、时序库、缓存等组件在最终版本中**并未使用**。保留此文仅作架构演进与设计思路记录。

## 多床位心电监护系统 新一代架构设计文档（Rust 工业级稳定版）
## 一、项目概述
### 1.1 项目背景与现状
现有系统为 .NET WPF + SQLite 双进程架构，已实现 8 床位生命体征的基础采集与展示。随着波形数据接入、7×24 无人值守、零丢包等要求升级，原架构已出现核心瓶颈：采集与存储强耦合导致 IO 阻塞丢包、SQLite 无法承载海量时序波形、前端轮询延迟高、长期运行存在 GC 抖动与内存泄漏风险。

本方案采用 Rust 生态构建工业级采集与后端服务，结合时序数据库、消息队列与 Web 前端渲染，打造一套**零 GC、内存可控、故障自愈、长期稳定运行**的医疗级监护系统，彻底解决丢包、卡顿、稳定性三大核心问题。

### 1.2 升级目标
- **零丢包**：接入层环形缓冲 + MQ 持久化 + 消费端确认，全链路数据不丢失；
- **超低延迟**：波形端到端延迟 < 150ms，前端 60fps 流畅滚动；
- **极致稳定**：Rust 内存安全 + 无 GC 停顿，支持连续运行 30 天以上无崩溃、无内存泄漏；
- **故障自愈**：设备断连、MQ 宕机、数据库离线均可自动恢复，数据零丢失；
- **高吞吐**：单端口轻松承载 8 台设备并发，未来可平滑扩展至数十台。

### 1.3 设计原则
1. **异步全链路**：从 TCP 接入到存储推送全程异步非阻塞，杜绝线程阻塞；
2. **分层强解耦**：接入、缓冲、消费、存储、推送五层独立，单层故障不向上向下扩散；
3. **内存零增长**：所有缓冲区固定大小，环形复用，运行期无内存持续增长；
4. **可靠性优先**：医疗数据场景下，数据完整性优先于极致性能；
5. **可观测性**：全链路指标监控 + 结构化日志，任何异常均可追溯定位。

## 二、需求与设备规格
### 2.1 功能需求
1. **设备接入**：单 TCP 端口接入 8 台监护仪长连接，自动识别科曼、迈瑞设备；
2. **协议解析**：完整解析 HL7 v2.6 协议，覆盖三类数据：
   - 生命体征：心率、血氧、呼吸、血压、灌注指数、心律失常参数等；
   - 心电波形：6 导联 ECG，兼容 250Hz / 500Hz 两种采样率；
   - 报警事件：分级报警（高/中/低），包含参数超限、导联脱落、噪声等；
3. **数据存储**：波形时序存储、体征与报警结构化存储，支持自动过期清理；
4. **实时可视化**：Web 前端 8 床位网格展示，波形滚动、体征更新、报警分级提示；
5. **历史回溯**：按床位、时间范围查询历史波形与体征数据；
6. **系统配置**：床位-IP 映射、报警阈值、数据保留周期可配置。

### 2.2 非功能需求
- 并发能力：单服务稳定承载 8 路 TCP 长连接，峰值 8 帧/秒波形数据；
- 丢包率：正常运行场景为 0，极端故障场景可补传、可追溯；
- 渲染性能：6 导联同时滚动，帧率 ≥ 50fps，主线程无阻塞；
- 资源占用：采集服务内存占用 < 100MB，CPU 单核占用 < 5%；
- 连续运行：30 天无服务崩溃、无内存泄漏、无数据错乱。

|------|------|------------|----------|----------|

## 三、整体架构设计
### 3.1 核心优化思路
| 原架构痛点 | 本方案解决方案 |
|------------|----------------|
| 采集直写数据库，IO 阻塞丢包 | 接入层仅投递 MQ，数据库性能完全不影响 TCP 接收 |
| SQLite 存波形，性能差、膨胀快 | TDengine 时序数据库，专为波形等高密度时序数据优化，压缩比 10~20 倍 |
| 前端轮询数据库，延迟高 | Redis 热缓存 + WebSocket 主动推送，毫秒级数据触达 |
| .NET GC 抖动，长期运行内存增长 | Rust 无 GC、手动内存管理，运行期内存平稳无抖动 |
| 无故障自愈机制 | 设备自动重连、MQ 本地兜底缓存、数据库离线堆积恢复 |
| 无全链路监控 | Prometheus + Grafana 指标监控 + ELK 日志追溯 |

### 3.2 分层架构总览
系统分为六层，严格单向依赖：
```
设备接入层 → 消息缓冲层 → 业务消费层 → 持久化存储层 → 缓存推送层 → 前端可视化层
                                                              ↓
                                                          运维监控层
```

### 3.3 完整数据流
1. 8 台监护仪建立 TCP 长连接，统一接入 Rust Tokio TCP Server（单端口）；
2. 接入层按设备分配独立环形缓冲区，完成粘包拆包、帧校验、HL7 解析，标准化后投递 RabbitMQ；
3. Rust 消费服务从 MQ 拉取数据，按类型分流处理：
   - 波形数据：批量聚合 → 写入 TDengine → 更新 Redis 热缓存；
   - 生命体征：写入 PostgreSQL → 更新 Redis 缓存；
   - 报警事件：写入 PostgreSQL → 触发 WebSocket 实时推送；
4. Tokio WebSocket 服务订阅 Redis 变更，向前端推送波形片段、体征更新与报警事件；
5. 前端 Vue3 应用通过 WebWorker 解析数据，OffscreenCanvas 离屏渲染波形；
6. Prometheus 采集全链路指标，Grafana 可视化大盘，ELK 存储全量日志。

### 3.4 完整技术栈
| 层级 | 技术选型 | 选型理由 |
|------|----------|----------|
| 设备接入 | Rust 1.75+ + Tokio 异步运行时 + 无锁环形缓冲区 | 零 GC、内存安全、百万级长连接能力，医疗工业级稳定性首选 |
| 协议解析 | Rust 自研 HL7 解析器 + Protobuf 内部标准化 | 零拷贝解析，性能远超通用解析库 |
| 消息队列 | RabbitMQ 3.12+（持久化队列 + 生产者确认 + 消费者手动 ACK） | 可靠性成熟，医疗场景广泛验证 |
| 业务消费 | Rust 多线程消费 / Go 消费服务（二选一） | 高并发、低资源占用 |
| 时序数据库 | TDengine 3.x | 国产物联网时序库，按设备分表，压缩比高，Windows 部署友好 |
| 关系数据库 | PostgreSQL 16 | 高并发写入稳定，JSON 原生支持，分区表成熟 |
| 缓存与发布订阅 | Redis 7.x（Stream + Hash + Pub/Sub） | 热数据缓存 + 实时事件通知 |
| 实时推送 | Rust Tokio WebSocket | 异步高并发，与接入层技术栈统一 |
| 前端 | Vue 3 + TypeScript + OffscreenCanvas + WebWorker | 离屏渲染 + 多线程解析，波形渲染无卡顿 |
| 运维监控 | Prometheus + Grafana + ELK | 全链路指标监控 + 结构化日志回溯 |

## 四、分层详细设计
### 4.1 设备接入层（Rust + Tokio，核心防丢包）
#### 4.1.1 TCP 服务架构
基于 Tokio 异步 runtime 构建单端口监听服务，利用 TCP 五元组天然区分 8 台设备，每台设备对应一个独立的连接任务。
- 单端口监听：无需多端口，通过 `socketaddr` 识别设备 IP，匹配床位配置；
- 异步非阻塞：全程 `async/await`，单线程即可处理全部 8 路连接，无上下文切换开销；
- 内核参数优化：`SO_RCVBUF = 65536`，`TCP_NODELAY` 禁用 Nagle 算法，降低延迟。

#### 4.1.2 防丢包核心机制
1. **每设备独立无锁环形缓冲区（RingBuffer）**
   - 每个连接分配固定大小的字节环形缓冲区（容量按 2 秒峰值数据设计）；
   - TCP 读任务仅负责将内核数据拷贝到环形缓冲区，立即返回，不做任何解析；
   - 独立解析任务异步从环形缓冲区读取数据进行帧切分与解析，解析阻塞不影响 TCP 接收；
   - 缓冲区满时记录告警日志，优先保证最新数据不丢失。

2. **HL7 帧精准切分**
   - 按 HL7 标准帧边界 `\x0B`（帧头）、`\x1C\x0D`（帧尾）进行切分；
   - 不完整帧暂存缓冲区尾部，等待后续数据拼接，绝不截断丢弃半帧；
   - 完整帧校验通过后，再送入解析流程，避免解析异常影响缓冲区写入。

3. **连接保活与故障自愈**
   - 心跳检测：3 秒一次 TCP KeepAlive，15 秒无响应判定为死连接，自动释放资源；
   - 断线重连：设备断连后保留设备上下文，重连成功自动恢复数据接收；
   - 兜底落盘：MQ 不可用时，原始报文写入本地磁盘（按日期分文件），MQ 恢复后自动补发。

#### 4.1.3 HL7 解析器设计
- 零拷贝解析：基于字节切片直接定位字段，避免字符串分配，性能最优；
- 设备自动识别：从 MSH 段匹配 `NDMonitor` / `MINDRAY_N_SERIES`，自动选择对应解析分支；
- 输出标准化：解析后统一转换为内部 Protobuf 结构，屏蔽厂商差异，下游无需感知设备类型。

### 4.2 消息缓冲层（RabbitMQ，核心解耦）
#### 4.2.1 队列划分
按数据类型拆分 4 个独立持久化队列，避免资源抢占与优先级倒挂：
| 队列名称 | 数据内容 | 优先级 | 持久化 | 消费模式 |
|----------|----------|--------|--------|----------|
| ecg_wave | 标准化波形帧（6 导联采样数据） | 普通 | 是 | 批量消费，批量入库 |
| ecg_vital | 生命体征数值 | 普通 | 是 | 单条/小批量消费 |
| ecg_alarm | 报警事件 | 高 | 是 | 立即消费，实时推送 |
| ecg_raw | 原始报文备份（可选） | 低 | 是 | 异步落盘归档 |

#### 4.2.2 可靠性机制
- **生产者确认（Publisher Confirm）**：投递后等待 Broker ACK，失败则重试或落本地盘，确保消息到达 MQ；
- **消息持久化**：所有队列开启 `durable`，消息标记为持久化，RabbitMQ 重启数据不丢失；
- **消费者手动 ACK**：消费端完成数据库写入 + 缓存更新后，才向 MQ 发送确认，处理失败消息重新入队；
- **死信队列**：多次消费失败的消息进入死信队列，避免阻塞正常消费，支持人工排查。

### 4.3 业务消费层
独立的 Rust 消费服务，与接入服务部署解耦，可单独水平扩展。
1. **多线程分流消费**
   波形、体征、报警使用独立的消费者组，分配不同的线程池资源，保障报警低延迟、波形高吞吐。
2. **数据标准化与清洗**
   - 时区统一：科曼 UTC 时间统一转换为东八区；
   - 单位统一：全部转换为标准单位（mV、次/分、mmHg 等）；
   - 异常值过滤：范围校验，过滤明显超量程的脏数据并记录日志。
3. **批量聚合写入**
   - 波形数据：攒批策略（1 秒或 100 帧触发），批量写入 TDengine，IO 次数减少 90%；
   - 体征与报警：可单条写入，或小批量聚合。
4. **缓存同步更新**
   写入数据库的同时，原子更新 Redis 热缓存，保证缓存与数据库最终一致。

### 4.4 持久化存储层
采用「时序数据库 + 关系型数据库」混合架构，各司其职。

#### 4.4.1 时序数据库：TDengine
心电波形是典型高密度时序数据，绝对不能存入关系型数据库。
- **表设计**：以「床位 + 导联」为维度建立子表，物理隔离数据，查询与写入性能最优；
- **超高压缩**：心电采样数据压缩比 10~20 倍，大幅降低磁盘占用；
- **自动过期**：配置数据保留策略（默认 7 天），超期自动清理，无需手动运维；
- **写入接口**：使用官方 Rust 连接器，批量写入 API。

**超级表定义：**
```sql
CREATE STABLE ecg_wave (
    ts TIMESTAMP,
    sample_data BINARY(4096),  -- 差值压缩后的采样数组
    sample_count SMALLINT,     -- 本帧采样点数量
    sample_rate SMALLINT,      -- 采样率 Hz
    resolution FLOAT           -- 分辨率 mV/单位
) TAGS (
    bed_no SMALLINT,
    lead_name NCHAR(10),       -- I/II/III/aVR/aVL/aVF
    device_ip NCHAR(15),
    device_model NCHAR(30)
);
```

#### 4.4.2 关系型数据库：PostgreSQL
存储结构化业务数据，支持复杂查询与事务。
1. **床位设备表**：存储床位与 IP 映射、设备型号、序列号、阈值配置；
2. **生命体征表**：按时间分区（按月），存储历史体征记录，建立联合索引；
3. **报警事件表**：记录所有报警的起止时间、类型、优先级、触发值，支持统计分析；
4. **系统配置与日志表**：存储操作日志、设备上下线记录。

#### 4.4.3 数据生命周期
- 实时波形：保留 7 天，超期自动删除；
- 生命体征：保留 1 年，超期归档冷存储；
- 报警事件：按医疗法规要求保留，默认永久；
- 原始报文：保留 7 天，用于问题排查。

### 4.5 缓存与实时推送层
#### 4.5.1 Redis 热缓存设计
所有前端实时展示数据全部走缓存，不查询数据库。
| Key 结构 | 类型 | 说明 | 更新策略 |
|----------|------|------|----------|
| `bed:{id}:vital` | Hash | 最新一条生命体征全字段 | 新数据到达原子更新 |
| `bed:{id}:wave:{lead}` | List | 最近 10 秒波形采样点，固定长度环形列表 | 新帧写入时右侧推入，左侧弹出 |
| `bed:{id}:active_alarms` | Set | 当前活跃的报警 ID 集合 | 报警 start 加入，end 移除 |
| `system:device_status` | Hash | 所有设备在线状态 | 连接建立/断开时更新 |

#### 4.5.2 WebSocket 推送服务
基于 Tokio WebSocket 实现高性能推送服务：
- 订阅 Redis Pub/Sub 频道，数据更新后立即推送给订阅客户端；
- 支持按床位订阅，客户端仅接收关注的床位数据，节省带宽；
- 波形分片推送：每次推送 200ms 数据，避免大包阻塞；
- 连接保活：30 秒心跳，断线自动重连，重连后补传缺失数据片段；
- 单服务可承载上千客户端并发连接，满足多终端展示需求。

### 4.6 前端可视化层（Web 版）
#### 4.6.1 技术架构
- 基础框架：Vue 3 + TypeScript + Pinia 状态管理；
- 渲染核心：**OffscreenCanvas 离屏渲染 + WebWorker 数据解析**；
- 通信：原生 WebSocket，二进制协议传输波形数据。

#### 4.6.2 波形流畅渲染方案
1. **多线程分离**
   - 主线程：仅负责 UI 交互与最终画面呈现；
   - WebWorker：负责接收 WebSocket 数据、二进制解压、数值换算，处理完将像素数据传给渲染线程；
   - 彻底避免数据解析阻塞主线程导致的卡顿。
2. **离屏渲染与滑动窗口**
   - OffscreenCanvas 后台绘制，不占用 DOM 资源；
   - 滑动窗口机制：仅保留可视区间（默认 10 秒）采样点，内存占用恒定，不随时间增长；
   - 增量滚动绘制：波形左移 + 右侧补绘新数据，避免全帧重绘，性能提升数倍。
3. **刷新策略**
   - 渲染帧率：50fps（20ms 刷新一次），兼顾流畅度与功耗；
   - 后台降频：页面不可见时自动降至 1fps，节省 CPU 与内存。

#### 4.6.3 界面与报警展示
- 布局：2×4 网格 8 床位卡片，每卡片显示体征数值 + 单导联波形，支持点击展开多导联详情；
- 报警分级：
  - 高优先级（H）：红色背景快速闪烁，弹窗提示；
  - 中优先级（PM）：黄色背景慢速闪烁；
  - 低优先级（PL）：蓝色文字提示，不闪烁。

### 4.7 运维监控层
#### 4.7.1 指标监控（Prometheus + Grafana）
全链路核心指标采集，可视化大盘展示：
- **接入层**：TCP 连接数、每秒接收帧数、缓冲区占用率、丢包计数、解析错误数；
- **MQ 层**：各队列消息堆积量、生产速率、消费速率、确认延迟；
- **存储层**：写入 TPS、查询耗时、磁盘使用率、连接数；
- **推送层**：WebSocket 连接数、推送延迟、每秒消息数；
- **系统层**：CPU、内存、磁盘、网络使用率。

#### 4.7.2 日志系统（ELK）
- 全链路 TraceID：从设备接入到存储推送携带统一 TraceID，问题可全程追溯；
- 分级日志：Error / Warn / Info / Debug，生产环境默认 Info 级别；
- 原始报文日志：可选存储原始 HL7 报文，用于协议问题排查。

#### 4.7.3 告警机制
- 队列堆积超过阈值告警；
- 设备离线超过 1 分钟告警；
- 服务进程异常退出告警；
- 磁盘使用率超过 80% 告警。

## 五、HL7 协议解析规范（Rust 实现）
### 5.1 设备识别
通过 MSH-3 发送方应用字段匹配：
- 包含 `NDMonitor` 或 `COMEN` → 科曼设备；
- 包含 `MINDRAY_N_SERIES` → 迈瑞设备；
- 结合 TCP 连接 IP 匹配床位配置，绑定床位号与设备信息。

### 5.2 报文类型路由
| 数据类型 | 消息类型 | OBR 观测标识 | 处理分支 |
|----------|----------|--------------|----------|
| 生命体征 | ORU^R01 | `182777000^monitoring of patient^SCT` | 体征解析器 |
| 心电波形 | ORU^R01 | `CONTINUOUS WAVE` / `MON_WAVE` | 波形解析器 |
| 报警事件 | ORU^R40 | `196616^MDC_EVT_ALARM^MDC` | 报警解析器 |

### 5.3 生命体征字段映射
| 参数 | 通用 MDC 代码 | 科曼 | 迈瑞 | 单位 |
|------|---------------|------|------|------|

| 血氧饱和度 | 150456 | ❌ | ✅ | % |

| 有创舒张压 | 150038 | 150034 | 150038 | mmHg |
| 灌注指数 | 150488 | ❌ | ✅ | % |

### 5.4 波形解析规范
#### 迈瑞波形
- 采样率：500Hz，每帧 500 点/导联；
- 数据类型：有符号整数；
- 换算：`实际电压(mV) = 采样值 × 0.001221`；
- 无效值：32767 表示导联不可操作，过滤处理。

#### 科曼波形
- 采样率：250Hz，每帧 250 点/导联；
- 数据类型：无符号 12 位整数（0-4095），基线 2046；
- 换算：`偏移量 = 采样值 - 2046`，乘以增益系数得到实际电压；
- 增益系数根据设备型号配置。

#### 兼容性处理
- 兼容迈瑞不同固件的 MDC 代码差异（采样率、INOP 字段多编码适配）；
- 统一输出结构：`(时间戳, 导联, 采样率, i16 采样数组, 分辨率)`。

### 5.5 报警解析规范
- 提取报警代码、触发参数、触发值、阈值范围；
- 解析属性：事件阶段（start/end）、状态、优先级（H/PM/PL）、类型（参数/状态）；
- 维护迈瑞私有编码 `99MNDRY` 映射表，兼容厂商扩展。

### 5.6 通用处理
- 时区统一：科曼 UTC 时间 → 北京时间；
- 编码统一：UTF-8；
- 缺失字段：置空，展示层沿用上次有效值。

## 六、核心稳定性保障机制
### 6.1 零丢包保障体系
1. **接入层双缓冲**：内核缓冲区 + 用户态环形缓冲区，解析阻塞不丢 TCP 报文；
2. **传输双确认**：生产者 ACK 确保入队，消费者手动 ACK 确保处理完成；
3. **持久化兜底**：MQ 消息落盘、数据库持久化，服务重启数据不丢；
4. **极端故障兜底**：MQ/数据库故障时，接入层本地磁盘缓存原始报文，恢复后自动补发；
5. **可追溯**：原始报文日志保留 7 天，任何丢包均可定位发生环节。

### 6.2 内存平稳保障
- 所有缓冲区固定大小，环形复用，运行期不分配新的大内存；
- Rust 所有权机制，无 GC，无内存泄漏；
- 前端滑动窗口固定长度，波形数据不无限累积。

### 6.3 故障自愈能力
| 故障场景 | 自愈机制 |
|----------|----------|
| 设备断网/断电 | 自动检测死连接，设备恢复后自动重连，继续接收数据 |
| RabbitMQ 宕机 | 接入层本地落盘缓存报文，MQ 恢复后自动补发，期间设备连接不受影响 |
| 数据库离线 | MQ 持续堆积消息，数据库恢复后消费端自动追平，数据无丢失 |
| 前端网络中断 | WebSocket 自动重连，重连后从 Redis 拉取最新缓存补全波形 |
| 服务进程重启 | 所有持久化数据保留，启动后自动恢复连接与消费，无数据丢失 |

### 6.4 性能兜底
- 流量控制：波形爆发时，接入层滑动窗口限流，优先保证完整帧不丢；
- 消费降级：队列堆积过高时，优先处理报警与体征，波形批量入库粒度加大；
- 过载保护：缓冲区使用率超过 80% 时触发告警，提前干预。

## 七、部署与实施方案
### 7.1 单机部署拓扑（8 设备规模）
单台 Windows 服务器即可承载全部组件，拓扑如下：

```
        │
        ▼
Windows 服务器
┌───────────────────────────────────────────────┐
│  Rust TCP 采集服务 (端口 5000)                 │
│  RabbitMQ 消息队列                             │
│  Rust 消费服务                                 │
│  TDengine 时序数据库                           │
│  PostgreSQL 关系数据库                         │
│  Redis 缓存 + Pub/Sub                          │
│  Rust WebSocket 推送服务                       │
│  Prometheus + Grafana 监控                     │
│  Elasticsearch + Logstash + Kibana 日志        │
└───────────────────────────────────────────────┘
        │
        ├─────────────┬─────────────┐
        ▼             ▼             ▼
   护士站 Web     医生办公室 Web   移动端 Web
   浏览器         浏览器          浏览器
```

### 7.2 部署要求
- 操作系统：Windows 10/11 / Windows Server 2019+；
- 硬件建议：CPU i5 及以上，内存 ≥ 16GB，SSD 磁盘（时序写入对 IO 敏感）；
- 网络：设备与服务器同局域网，静态 IP，防火墙开放 5000（TCP 采集）、80/443（Web）端口。

### 7.3 服务化部署
- 所有 Rust 服务编译为独立 exe，通过 Windows Service 方式安装，开机自启；
- RabbitMQ、Redis、TDengine、PostgreSQL 均配置为系统服务，自动启动；
- 前端静态资源通过 Nginx 部署。

### 7.4 平滑迁移方案
1. **并行验证阶段**：新老采集服务同时监听（端口复用或设备双发），双写数据，对比一致性；
2. **前端切换阶段**：验证数据一致后，前端切换为新系统 Web 页面；
3. **下线旧系统**：稳定运行 7 天无异常后，停止旧服务，完成迁移。

## 九、避坑清单
1. **绝对禁止跳过 MQ 直写数据库**：数据库任何 IO 抖动都会反向阻塞 TCP 接收，必然丢包；
2. **绝对禁止用关系库存波形**：PostgreSQL/MySQL/SQLite 都不适合每秒数千至上万采样点的写入与查询，会迅速性能崩塌；
3. **解析逻辑不能阻塞 TCP 读**：接收与解析必须分线程/分任务，用缓冲区解耦；
4. **前端禁止主线程解析波形数据**：必须放入 WebWorker，否则数据量大时必然掉帧卡顿；
5. **重视设备固件差异**：同品牌不同型号/固件的 HL7 字段、编码存在差异，必须做多版本兼容；
6. **时区问题必须前置处理**：科曼 UTC 时间若不转换，会导致时间线错乱、历史查询异常。

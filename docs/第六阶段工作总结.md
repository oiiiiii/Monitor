# 第六阶段工作总结：缓存与实时推送层

**完成时间**：2026-06-27

---

## 一、阶段目标

本阶段实现心电监护系统的缓存层与实时推送层，为前端提供低延迟的数据访问能力：

1. **Redis 缓存模块**：缓存热点数据（最新体征、最近波形、活跃报警、设备状态），降低数据库压力
2. **WebSocket 推送服务**：建立实时双向通信通道，按床位订阅推送
3. **波形分片推送**：按 200ms 时间片推送波形数据，平衡实时性与带宽
4. **报警优先推送**：报警事件最高优先级，立即推送给前端

## 三、核心模块实现

### 3.1 Redis 缓存模块

**文件位置**：`monitor-common/src/cache/redis_cache.rs`

#### 缓存数据结构

| 数据类型 | Redis 结构 | Key 格式 | TTL | 说明 |
|---------|-----------|----------|-----|------|
| 生命体征 | Hash | `vital:{bed_no}` | 30s | 最新一次体征数据 |
| 波形数据 | List | `wave:{bed_no}:{lead}` | 60s | 最近 10 秒波形点（环形列表） |
| 活跃报警 | Sorted Set | `alarms:active` | 300s | 按优先级排序的活跃报警 |
| 设备状态 | Hash | `device:{device_id}` | 60s | 设备在线状态、最后在线时间 |

#### 关键方法

- `update_vital_signs(vital)` — 更新体征缓存
- `append_waveform(wave)` — 追加波形点，保持固定长度（LPUSH + LTRIM）
- `update_alarm(alarm)` — 更新报警状态（开始/结束）
- `update_device_status(device)` — 更新设备在线状态
- `get_latest_vital(bed_no)` — 获取最新体征
- `get_recent_waves(bed_no, lead, count)` — 获取最近 N 个波形点
- `get_active_alarms(bed_no)` — 获取某床位活跃报警

### 3.2 WebSocket 推送服务

**文件位置**：`monitor-push/src/websocket/`

#### 模块结构

| 文件 | 职责 |
|------|------|
| `mod.rs` | 模块导出 |
| `message.rs` | 消息格式定义（推送消息 + 客户端消息） |
| `session.rs` | 客户端会话管理 + 连接管理器 |
| `server.rs` | WebSocket 服务器（Tokio Tungstenite） |

#### 推送消息格式

```json
{
  "msg_type": "vital_signs | waveform | alarm | device_status | heartbeat",
  "bed_no": 1,
  "timestamp": 1719475200000,
  "data": { ... }
}
```

#### 客户端操作

```json
{
  "action": "subscribe | unsubscribe | ping | request_history",
  "bed_no": 1
}
```

#### 核心特性

- ✅ 按床位订阅机制（`ClientSession.subscribed_beds`）
- ✅ 心跳保活（默认 30 秒一次）
- ✅ 最大连接数限制（可配置）
- ✅ Ping/Pong 协议级心跳
- ✅ 优雅断开 + 自动清理

### 3.3 数据推送管道

**文件位置**：`monitor-push/src/pipeline.rs`

#### 三路并行消费

推送管道从 RabbitMQ 三个队列并行消费数据：

| 队列 | 优先级 | 推送策略 | 缓存更新 |
|------|--------|----------|----------|
| `ecg_alarm` | 最高 | 立即推送 | 更新活跃报警集合 |
| `ecg_vital` | 中 | 准实时推送 | 更新体征 Hash |
| `ecg_wave` | 低 | 分片推送 | 追加波形 List |

> **设计说明**：推送服务使用 `no_ack: true` 自动确认，因为推送层不负责数据持久化（已由阶段五的消费者写入数据库），即使推送服务重启也不影响数据完整性。

#### 推送流程

```
MQ 消息 → 解析数据 → 更新 Redis 缓存 → 广播给订阅客户端
                              ↓
                        (异步任务，不阻塞推送)
```

### 3.4 monitor-push 主程序

**文件位置**：`monitor-push/src/main.rs`

#### 启动流程

1. 初始化日志（tracing + tracing-subscriber）
2. 加载配置（从环境变量）
3. 初始化 Redis 缓存（后台连接，不阻塞启动）
4. 创建 WebSocket 服务器
5. 启动三路推送管道（vital/wave/alarm）
6. 启动 WebSocket 监听
7. 等待 Ctrl+C 信号，优雅关闭

#### 配置项

| 配置项 | 环境变量 | 默认值 | 说明 |
|--------|---------|--------|------|
| 监听地址 | `PUSH_LISTEN_ADDR` | `0.0.0.0` | WebSocket 监听地址 |
| 监听端口 | `PUSH_LISTEN_PORT` | `8080` | WebSocket 监听端口 |
| 心跳间隔 | `PUSH_HEARTBEAT_SECS` | `30` | 心跳间隔（秒） |
| 最大连接数 | `PUSH_MAX_CONNECTIONS` | `1000` | 最大客户端连接数 |
| 波形分片 | `PUSH_WAVE_SLICE_MS` | `200` | 波形分片时长（毫秒） |
| Redis 地址 | `PUSH_REDIS_HOST` | `127.0.0.1` | Redis 主机 |
| Redis 端口 | `PUSH_REDIS_PORT` | `6379` | Redis 端口 |

## 六、技术亮点

### 6.1 分层缓存策略

- **热点数据全内存**：体征、波形、报警全部缓存在 Redis，前端查询毫秒级响应
- **自动过期清理**：所有缓存带 TTL，设备离线后自动清理，避免内存泄漏
- **波形环形列表**：使用 LPUSH + LTRIM 维护固定长度，O(1) 复杂度

### 6.2 优先级推送机制

- 报警事件独立消费线程，零延迟推送
- 体征数据准实时推送
- 波形数据批量推送，减少网络 IO
- 三路并行，互不阻塞

### 6.3 高可用设计

- 推送层无状态，可水平扩展
- Redis 故障不影响推送（降级为仅实时推送）
- MQ 故障自动重连（基于 lapin 内部机制）
- 客户端异常断开自动清理会话
